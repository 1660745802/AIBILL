# 功能取舍流程 · Feature Triage

> **一句话：用数据决定功能去留，不用直觉。**
>
> 一个功能「没人用」和「不存在」是两回事。前者可能是入口太深，后者是压根没做。
> 这两种情况在代码里长得几乎一样（都有完整的四层数据链路），但处置方式完全不同。
> 这份文档就是怎么在不重新调研一遍的前提下，把两者分开。

跑一次体检脚本，10 秒拿到证据：

```bash
scripts/feature-triage.sh
```

---

## 1. 为什么要写这个流程

2026-10 做前端重做时，我们顺手做了一次功能体检，结果推翻了自己的一个判断：

- 我看到「预算 3 个月 0 行」，判定为无价值，下线了 Web 端，**并保留了后端接口**，理由是「怕影响移动 App」
- 让 Android 端自查后发现：它有 `BudgetApi` / `BudgetRepository` / `BudgetResponse` / Hilt 绑定**四层数据链路齐备**，但 `presentation/` 层**零引用** —— UI 入口从未做过

也就是说，「保留接口以兼容客户端」这个决定本身是错的：**客户端在技术上依赖、在事实上不可达**。
如果只查服务端表行数就下结论，会得出一个看起来稳妥、实际误导后来人的结论。

所以这个流程的核心不是「看数据」，是**数据 + 客户端可达性必须一起看**。

---

## 2. 四类证据

按可信度从低到高叠加。**只看第一类就会出错。**

### 2.1 表行数 —— 最弱的一类

```
budgets            0      ← 建了从来没人用
financial_goals    0
```

只能说明「服务端没数据」。无法区分「功能没用」和「功能不存在」。

用 `scripts/feature-triage.sh` 输出，或手工：

```sql
select 'budgets' t, count(*) from budgets
union all select 'financial_goals', count(*) from financial_goals;
```

### 2.2 最近写入时间 —— 判断是不是「用了一阵就废了」

```
invite_codes       1      2026-07-02   ← 三个月前，最后一次
users              3      2026-07-02
transactions     551      2026-10-09   ← 活跃
```

行数不为 0 但长期没动，说明功能曾经有用但已经失效，价值判断要更谨慎。

### 2.3 请求日志 —— 判断「主入口在哪」

```
 613  POST /api/ai/parse
 182  POST /api/transactions
  26  POST /api/admin/updates
```

⚠️ **两个已知陷阱**：

- **`app_logs` 只记写操作，不记 GET。** 所以「日志里没出现 `/api/budgets`」**不能**证明没人调它。
  本仓库的 `logger` 只对 mutation 打点。要统计读调用得看网关/反代日志，或者先给 logger 补 GET。
- **日志窗口要够长。** 脚本会打印覆盖区间，**不足 30 天会给出警告**——三个月的 0 行和一周的 0 行不是一个结论。

### 2.4 客户端可达性 —— 决定性的一类，必须跨仓库查

直接问客户端开发者，或者 grep 对方仓库。**要看 UI 层，不是数据层。**

```bash
# 数据层：有
grep -rn "budgets" app/src/main --include=*.kt
#   → BudgetApi / BudgetRepository / BudgetResponse / Hilt 绑定 都有

# UI 层：没有
grep -rn "BudgetRepository\|BudgetApi" app/src/main/java/**/presentation/ --include=*.kt
#   → 0 处
```

**判定**：接口声明存在 + UI 零引用 = 事实上的死代码。保留它只会让下一个人误以为功能还在用。

## 3. 处置矩阵

| 服务端 | 客户端可达 | 处置 |
|--------|-----------|------|
| 有数据 | 有 | 正常使用 |
| 有数据 | 无 | 确认客户端是否要接；不接则清数据 |
| **0 行** | **有** | **不要删接口**，先问客户端：是没做好还是不需要 |
| **0 行** | **无** | **可以下线** —— 但见 §4 的安全规则 |

还有一个反直觉的情况：

| 服务端 | 客户端 | 真相 |
|--------|--------|------|
| 调用量大 | — | **主入口在这里**，应该给它最大权重 |

2026-10 的实测：

```
记账来源：app_notification 501 (91%) / manual 42 (8%) / ai 8 (1%)
```

91% 的记账来自 Android 通知自动入账。这个数字直接改变了 Web 端的导航层级排序。

---

## 4. 安全规则

功能下线是**破坏性变更**，且本项目是多客户端的。固定动作顺序：

1. **先撤前端入口，不动后端。** 页面删掉、导航项摘掉，接口留着。
2. **标 `deprecated`，不要写「保留」。** 「保留」会被后来人读成「还在用」。
   把判定依据也写进去（表行数、客户端可达性），免得下一个人重新调研：

   ```markdown
   | 功能 | 废弃的接口 | 客户端现状（2026-10 核查） |
   |------|-----------|----------------|
   | 预算管理 | `/api/budgets/*` | Web 已下线；Android 数据层四层齐备但 presentation 层零引用（未做 UI 入口） |
   ```

3. **响应结构不动。** 即使对应字段恒为空，也保留在响应里——客户端的解析逻辑不该因为服务端「不写了」而炸。
4. **旧路由 302 到合理落点**，不要 404。App 或收藏夹里的旧链接不该报错。
5. **DROP 表要等客户端先删完。** 生产库的 DROP 不可逆，且跨仓库有先后顺序。
6. **删表前先确认真的 0 行。** 脚本的输出就是这一步的凭据。

---

## 5. 节奏

**每半年复盘一次**，用同一份脚本，让导航和功能跟着真实使用走。

不要因为「感觉这个功能没人要」就动——先用脚本看一眼。上一次复盘推翻了一个凭直觉做的兼容性决定。

---

## 6. 体检脚本会额外发现的东西

跑脚本本身就有独立价值。2026-10 第一次运行时，它发现了三个手工调研时漏掉的表：

```
goal_progress       0      ← goals 的从属表，之前完全没注意到
recurring_patterns  0      ← Android 智能分类学习的落地表
user_settings       0      ← 而 settings 有 6 行：疑似重复/遗留表
```

手工查「我印象中的那几个功能」一定会漏表。`sqlite_master` 全量扫不会。

> `user_settings` 尤其值得警惕——`settings` 有数据而它没有，通常意味着某次重构留下了旧表，
> 写入路径已经迁移但表没删。
